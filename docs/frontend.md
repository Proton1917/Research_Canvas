# Research Canvas 前端

前端是一个 React 19 单页应用，文稿和画布共用 `src/editor/` 中的编辑能力。所有数据来自 Rust 服务的 `/api` 接口，调用约定见 [api.md](api.md)。界面流程与实测截图见 [design/flow/index.html](design/flow/index.html)。

## 启动

在项目根目录执行（脚本加载 `scripts/environment.sh` 中的项目内 Node 22.23.4 与 Yarn 4.7.0）：

```bash
bash scripts/web.sh install     # 按 yarn.lock 安装依赖
bash scripts/backend.sh start   # 后端，默认 127.0.0.1:8787
bash scripts/web.sh dev         # 开发服务 http://127.0.0.1:5173，/api 代理到后端
```

Vite 开发代理从 `config/server.toml`（缺失时用 `config/server.example.toml`）读取后端地址；环境变量 `RESEARCH_CANVAS_API` 可改为其他地址。

| 命令 | 作用 |
| --- | --- |
| `bash scripts/web.sh typecheck` | `tsc --noEmit`，覆盖 `src/` 下全部 TypeScript |
| `bash scripts/web.sh build` | 类型检查后构建到 `dist/`；后端按 `frontend_directory = "dist"` 直接托管，访问 `http://127.0.0.1:8787/` |
| `bash scripts/web.sh preview` | 在 5173 预览 `dist/` |

模块别名以 `tsconfig.json` 的 `paths` 为唯一来源（`@editor/*`、`@research`、`@research/editor`、`@ui`），`vite.config.ts` 读取同一份配置。Vite 缓存位于 `.runtime/vite-cache/`。

## 数据约定

- **文稿保存**：每次保存同时提交文本块投影、Markdown 与 `editor_state`（`blocksuite-yjs-v1`，Y.Doc 更新的 Base64）。编辑后约 1.2 秒自动保存，页面隐藏时立即保存。版本冲突（409）时保留本地内容，用户可选择保留本地或载入服务器版本。
- **文本块投影**：块标识沿用编辑器块标识。标题、引用、列表、代码、公式块写成 Markdown 前缀，行内公式写成 `$…$`，表格写成 GFM 表格。投影可逆：服务端改写清除 `editor_state` 后，前端按文本块重建结构。投影规则新增块类型后，已保存文稿首次打开时自动补存一次文本块，编辑状态保持不变。
- **锚点**：选段按块内投影文本的 UTF-16 偏移记录，并附带文稿版本。原文修订后由后端返回原位、已重定位、原文已改、定位失效或多处匹配。
- **保存一致性**：文稿与画布各自维护编辑序号 `seq` 与已确认序号 `savedSeq`。保存在第一次等待前同步取快照，保存期间的新编辑在完成后按序号补存。切换工作区、发起场景上下文和应用画布提案前执行 `flushAll`/`flushCanvas`；仍有未保存或失败的条目时弹出确认框，列出条目与错误，由用户选择重试或放弃。AI 画布提案新建的文稿首次打开时只做 Markdown 结构转换，不立即写回；首次编辑、创建批注或发起上下文时再保存，因此未改动的候选文稿可整组撤销。`flushAll`（页面隐藏或刷新、切换工作区、导出）跳过这类仅有显示转换的文稿，服务端版本保持不变。
- **首次打开的 Markdown 来源**：`markdownSource` 对带 `markdown` 字段的 document、单块 discussion 及带 `metadata.canvas_proposal_id` 的单块 note 取 Markdown 原文，经 `MarkdownTransformer.importMarkdownToBlock` 建立标题、列表、加粗与公式。已有 `editor_state` 或历史编辑状态的文稿按保存内容载入，不再转换。画布卡片与精读视图共用同一文稿 store，显示一致。
- **画布**：卡片是 `affine:embed-synced-doc`，引用统一文稿；同一文稿可出现在多张画布。画布标题栏下方是固定高度的选择操作行（提问、展开编辑、研究联系等），选择变化时画布位置保持不变。`editor_state` 使用 `view_version: 2`：
  - `link_views`：连线标识 → `{relation_id, source_instance, target_instance, detached_from}`。
  - `hidden_relations`：本画布隐藏的研究关系。
  - `fragments`：片段卡片 → 锚点及版本。
  - 旧版 `links` 读取时迁移。

  视觉连线与研究关系分开保存，规则如下：
  - 删除连线只隐藏本画布的显示，研究关系保留，刷新和切换工作区后不重新生成。
  - “在本画布显示”只在移除了隐藏记录或连线视图实际变化时写入画布布局。两端未都放置时不写入，并逐端说明原因，如“属于画布「主画布」”或“尚无片段卡片在本画布”。
  - 画线、改接和删线只更新本画布的 `link_views`，研究关系集合不变。改接已绑定的连线解除绑定并记录 `detached_from`。
  - 研究关系由用户显式建立：选中未绑定的连线，点“研究这个联系”，填写一句说明（可空）后“建立候选联系”。关系以 `claim.status = candidate` 创建，说明写入 `label`，并绑定该连线。
  - 关系的语义端点与连线的视觉端点分别保存：关系记录 `source_ref`/`target_ref`，`link_views` 记录两端画布实例。
  - 研究关系只通过显式“删除研究关系”删除，删除后各画布移除对应连线。
- **场景上下文**：多选卡片、片段、想法、连线和讨论后，用 `projectScene` 生成世界坐标、视口、框内成员、连线端点、公式及版本，再与材料清单一起提交 `POST /workspaces/{id}/scene-contexts`。
  - 材料分为正文、图像、历史来源与定位四组，`include` 决定阅读范围。默认只勾选明确选择的对象；随分组或框纳入的对象、整篇正文和图像需要用户勾选。“加入附近对象”把选区周围 240 以内的对象加入选择，其材料默认不勾选。PDF 卡片初始只提供身份与定位。
  - 回答方式默认为“讨论框”：回答保存为讨论文稿，由后端按运行来源放回发问时的画布（见“异步讨论归位”）。“在画布上创建”使用 `mode=canvas` 并附写入区 `write_scope.bounds`；画布模式的运行若只返回讨论文稿（`document_id`），同样按讨论卡片归位。
  - 冻结：预览和发送都先保存选择范围内已载入的文稿与画布，再按保存后的版本重新投影，以问题、模式、勾选材料及版本、画布 revision、写入区、选择和图像作为快照身份。身份不变时复用已冻结上下文，否则建立新上下文。
  - 提问会话与代次：面板打开时建立会话标识，关闭时结束；会话内修改问题、勾选、选择、模式、写入区域、截图或离开所在画布都推进代次。冻结、截图发起时捕获会话、代次、工作区、编辑会话与画布操作对象，并在三处核对归属：
    1. 保存完成：代次已变化则结束本次发送，面板保留新输入并说明“冻结期间提问内容已变化，本次未发送”。
    2. 上下文返回：上下文记入上下文记录；代次已变化时面板不采用，也不发起运行。
    3. 运行创建返回：运行记入运行记录并继续跟踪；面板已切换或关闭时按 `run.origin` 归位。
    截图上传返回时代次已变化，截图不进入本轮，保留在截图列表中。同一画布的冻结（保存、重新投影、建立上下文）与讨论归位按顺序执行，冻结使用的画布版本与投影一致。
  - 发送返回 409 `stale_context` 时，问题、选择和勾选保留，面板列出变化对象（文稿 `v旧→v新`、画布 `r旧→r新`）。前端载入变化文稿的服务端版本；画布落后时按服务端画布重建并等待视图重新挂载，然后重新冻结，由用户再次发送。`GET /contexts/{id}/freshness` 可查询同样的信息。
  - 面板显示已冻结的字符数与 `max_input_characters`。`context_budget_exceeded` 时列出总字符数、上限与各来源长度，按长度排序，便于取消较长的来源。
  - 图像：“截取选区图像”用 `EdgelessClipboardController.toCanvas` 生成选区 PNG，经 `api.uploadVisual` 保存为提问截图资产，工作区文稿数量不变。画布中的图片对象与图片文稿提供“以图像读取”材料（图片文稿取 `metadata.source_asset_id`）。请求附 `visuals: [{asset_id, object_ids}]`，`object_ids` 取本轮选入的场景对象，因此至少保留一项材料才能发送。
    - 截图列表（`api.listVisualAssets`）显示缩略图、大小与引用数，可按已有截图“加入本轮”。截图行的关闭按钮只“移出本轮”；“永久清理”需再次确认后调用 `api.discardVisual`。截图已被冻结上下文、文稿、历史版本、画布或提案快照引用时，服务返回 `asset_in_use`，列表在该行列出引用位置，图像保留。
    - 附带图像而当前模型不在 `vision_models` 中时，面板先提示可改用的视觉模型；发送仍由服务判断。`vision_unsupported` 与 `image_budget_exceeded` 显示服务说明一次，问题、选择与勾选保留，由用户调整模型或材料后再次发送。
- **异步讨论归位**：成功且具有讨论文稿与 `origin`、`placement` 为 null 的运行等待放回发问时的画布。
  - 目标画布在前台并挂载后：暂停自动保存并写入本地编辑 → `api.placeRun(run.id, {expected_canvas_revision})`（冻结写入区为空时附视口附近的空位 `bounds`）→ 采用返回的运行与完整画布。后端在同一事务中生成讨论卡片、仍在画布上的来源连线与归位记录。
  - 目标画布在后台：主区顶部列出“讨论「…」待放回画布「…」”和“前往原画布”；运行记录与讨论面板的入口显示“放回原画布「…」”或“在原画布中定位”。提问框关闭、切换画布或文稿、刷新后均由运行列表恢复。
  - 409 按画布保存冲突处理：画布进入冲突状态并保留本地编辑；用户“保留本地内容”或“载入服务器版本”后自动再次归位。网络错误或 5xx 时读取运行记录，归位已保存则重复请求取回当前画布，卡片保持一份。
  - 事件流只更新运行所属工作区；用户在其他工作区时保留其视图，回到原工作区后由运行列表恢复。画布提案同样按 `proposal.canvas_id` 定位：目标画布在后台时提示“前往查看”，并列在顶部记录中。
- **画布提案**：运行完成后读取 `run.canvas_proposal_id` 和完整提案。候选框与候选连线显示在冻结的写入区内，可调整位置、标题和正文，也可排除单项。确认写入（能力 `canvas_proposal_materialization`）的步骤：
  1. 暂停画布自动保存并保存已有修改。画布版本与提案冻结时不同，需用户选择“按当前画布确认写入”。其他客户端已更新画布时，`apply` 返回 409；前端载入服务端画布并显示版本差异，用户确认后以新版本提交。
  2. 有调整或画布版本变化时，以 `PATCH` 提交调整后的操作集合（版本变化时附 `expected_canvas_revision`）。
  3. 调用 `apply`，只提交 `{expected_revision, expected_canvas_revision}`。后端在一个事务中生成文稿、关系、Yjs 状态与对象表。
  4. 采用响应中的完整画布与文稿版本。采用画布时先卸载旧编辑器，再销毁旧文档并重建。
  5. 恢复自动保存。

  `apply` 遇到网络错误或 5xx 时读取提案：状态为 `applied` 时以同一请求重复确认，取回原事务结果（服务端幂等）；否则提示画布未写入、可重试。运行记录按提案的实际状态显示入口（待确认、已写入、已撤销、已拒绝），刷新后自动读取状态。普通画布保存时对象表由后端按 Yjs 快照生成，前端采用响应的对象表。

  候选联系端点可以是文稿、新建框（`created`）、精确锚点（`anchor`）或场景实例（`scene`）。预览连线按以下规则定位：
  - 文稿取卡片，没有卡片时取该文稿的片段卡片。
  - 锚点取当前画布 `fragments` 中引用该锚点的片段卡片。
  - 场景端点直接使用 `object_id`。

  提案打开时，视口同时覆盖候选框和已在画布上的联系端点。撤销调用 `revert`。服务端返回依赖或版本冲突时保留当前内容并显示原因。拒绝不写入任何内容。
- **失败画布运行的恢复**：运行记录对失败的画布运行提供两项操作。
  - “从原输出恢复提案”调用 `POST /runs/{id}/recover-canvas-proposal`；成功后采用返回的运行，并打开提案。
  - JSON 内容本身无效时显示服务返回的具体错误，保留原输出与运行错误；此时可用“按原上下文重新生成”，以同一 `context_id` 发起新的结构化运行。
- **研究关系端点**：关系创建与修改支持类型化端点。
  - 文稿：`{type:'document', id}`。
  - 精确锚点：`{type:'anchor', id}`，对应片段卡片。
  - 冻结场景中的自由想法：`{type:'canvas_object', context_id, canvas_id, instance_id}`，对应便笺、文字、形状。

  对一条连线执行“研究这个联系”时，前端按两端实例确定端点类型（两端需为文稿卡片、片段卡片或带文字的想法，且不是同一对象）：
  - 两端都是文稿时沿用 `source_id`/`target_id`。
  - 含自由想法时，先保存画布，再以 `mode=relation` 冻结两端与连线的场景，然后用 `canvas_object` 引用其中的实例。

  关系标题、学科桥端点与证据候选按 `source_ref`/`target_ref` 解析：片段显示原文与版本；想法显示冻结时的文字，所需场景按需读取；旧 `source_id`/`target_id` 只作为不透明标识使用。画布按类型化端点补齐或恢复关系连线。
- **学科桥**：五种状态为启发、候选、有支持、已确立、被反驳；历史值 `verified` 显示为已确立。
  - 卡片先显示两端、状态与联系说明。结构对应、保持运算、成立条件、出处、反例、尚缺论证和验证方法收在“研究细节”中，有内容时默认展开，摘要显示已填项数。关系面板的“研究细节”只含条件、反例与出处，其余字段在学科桥中编辑。
  - `claim.missing_proof`（尚缺论证）和 `claim.next_validation`（下一步验证方法）作为研究内容编辑，随 `PATCH /relations/{id}` 保存。候选状态且记录了证据缺口时，卡片顶部显示“证据缺口 · 保持候选”，关系列表显示“证据缺口”标记。AI 候选联系的缺口与验证方法在提案面板中显示。
  - 状态升级通过 `POST /relations/{id}/review` 提交：带版本的锚点或整篇证据（支持/推导/反例）、判断依据，以及人工确认。
  - 编辑已有确认记录的关系时携带 `expected_claim_revision`。服务端标记 `review_required` 后显示“待复核”及上次确认的依据和证据版本，原判断保留。
- **打开工作区时的画布**：优先打开浏览器保存的 `rc:canvas:<workspace_id>`。该值缺失或指向已删除画布时，打开工作区画布列表的首项；服务按 `updated_at,id` 升序返回，首项是最久未更新的画布。
- **讨论**：侧栏讨论的预览与发送先保存所选文稿；材料在冻结后被修改时（`stale_context`）载入新版本并重新冻结。预览上下文与发送使用同一 `context_id`；生成结果以 SSE 流式显示，回答按 Markdown（含表格与公式）渲染并保存为讨论文稿。讨论脉络按上下文关系组织，合并讨论挂在最近的直接分支下。

## 验证记录

### 2026-10-26 画布提案便笺的 Markdown 显示

问题：画布「P0 归位 B 000319」（`6baeb427-…`）中的卡片 `JRAtU5xzzU`，对应文稿 `51e99000-61f6-4a83-9093-6e21a0290fae`（note，v1，由画布提案 `7bfdfdc6-…` 新建，`editor_state` 与 `markdown` 均为 null）。正文是单个文本块：`### 保持的结构与运算`，随后是三个 `- **…**：` 列表项，含行内公式。原先 `markdownSource` 不处理 note，这块正文走 `buildStoreFromBlocks`，被 `parseStructured` 整块当作 h3 标题，列表符号和 `**` 按字面显示。

修复：
